## 2. Introduction

The ChipInventor RVBL-2 is a microcontroller built around a RISC-V-based core, being manufactured using the 130nm Sky130 PDK. This guide serves as an architectural reference for using the microcontroller.

## 2.1 The Core

The microcontroller includes a RISC-V core that implements 32-bit ISA, operating with multiple clock cycles per instruction (i.e., multi-cycle). This approach allows the sharing of hardware resources (such as memory interfaces and arithmetic units) at different stages of execution, optimizing the chip area.

The kernel is compatible with the RISC-V standard specified in [1], implementing the base ISA RV32I (for 32-bit integer operations) as well as the standardized Zmmul extension (derived from the M extension for multiplication instructions only). It also implements a custom extension to calculate CRC called Xicrc.

The extension of RISC-V that standardizes this is M, which specifies multiplication and division instructions. Splitting instructions, however, greatly increase the area of the chip. ## 3. RISC-V Core

This section covers the internal organization of the RISC-V core, describing the main units that compose it. Many different organizations make it possible to implement the RISC-V architecture specified in [1] in a correct manner, allowing its normal use.

Therefore, this section seeks to bring the chosen implementation for this kernel, which involves a state machine using multiple clock cycles to control the kernel operation, as well as implementation of the extensions discussed above and other important modules for the correct implementation of the ISA RV32I instructions.

## 3.1 Core Datapath

It holds the core units of the kernel (shown in Figure 1), forming the path through which data travels during the execution of instructions.

## 3.1.1 ALU

In addition to calculating results for logical/arithmetic instructions, it is reused to calculate memory addresses (in loads/stores) and deviation targets (branches/jumps).

It is primarily composed of several combinational blocks that perform operations on inputs A and B. The result of each block is sent to a multiplexer that selects the result that should be passed on to the output based on a signal sent by the control unit. It is the unit responsible for performing the core multiplication operations.

It is composed of multiplexers that select which inputs should be sent to the block that will perform the multiplication (64 bits), as well as another multiplexer that selects which part of the final result should be sent to the output (the lower or upper 32 bits).

## 3.1.4 RISC-V Registers

The RISC-V core has 34 registers: 32 general purpose registers (in the register bank) at the user's disposal, the PC (program counter) and the IR (instruction register).

The register bank holds temporary CPU data. Contains 32 32-bit general-purpose registers (x0 to x31). The x0 register is hardwired (fixed) at zero and cannot be modified. Allows simultaneous asynchronous reading of the rs1 and rs2 operands, and synchronous writing of the rd target in the Write Back stage. The register selection signals are extracted directly from the instruction, and the write enable signal is sent by the control unit

The program counter (PC) tracks the execution stream while maintaining the 32-bit address of the current instruction. It is updated sequentially (PC+4) with each clock cycle or loaded with new addresses derived from flow control instructions (branch and jump). The RISC-V core uses the PC value to fetch the next instruction to execute.

The instruction register (IR) holds the 32 bits referring to the current instruction to be executed, fetched earlier in the Fetch cycle. Its contents are read by the other blocks and decoded to allow the correct execution of the instruction.

## 3.1.5 Immediate Extension

Module responsible for extracting and formatting the immediate values embedded in the RISC-V instructions, being completely combinational. Therefore, it decodes the instructions of type I, S, B, U, and J based on their opcode and extracts their immediate.

Therefore, it takes the bits scattered throughout the instruction (based on the formatting of the specific type of the instruction) and performs the signal extension to generate a valid 32-bit operand for the ALU.

## 3.1.6 Branch Comparator

Unit responsible for executing the conditional hop (or branch) statements. This module compares the rs1 and rs2 registers coming from the register bank based on the branch statement (selected by the funct3 field of the statement). The module also needs to worry about whether the comparison takes into account the signal or not.

Being a combinational module, it needs to obtain the input signals, along with the selection, make the desired comparison and inform whether the jump will be taken or not.


## 3.2 Control Unit

Component responsible for controlling the operation of the RISC-V core, being its most critical component. To do so, it internally implements a Finite State Machine (FSM) that controls the datapath, signaling which units should be used and how they should be used.

Thus, the internal FSM divides the execution into the following phases, each corresponding to a clock cycle:

- Fetch: Reads the instruction from the ROM using the current value of the PC and saves it to the instruction register (IR).

- Decode: Reads the operands from the Register Bank and decodes the instruction to determine the next states.

- Execute: ALU takes action to perform the main calculation of the instruction, calculate the effective memory address, or evaluate the condition of a deviation (Branch).

- Write Back: Saves the final result (coming from the ALU or RAM via LSU) in the destination register in the Register Bank.

The control unit then receives the opcode from the instruction and emits signals that will control the datapath, allowing it to be executed.

## 3.3 LSU (Load/Store Unit)

This module provides a direct interface between the RISC-V core and the memories. These devices can be accessed by the RISC-V core through addresses, as commented in section 4. Memory Mapping. These addresses map internal positions to devices that can be read or written by the kernel.

Therefore, LSU has two main functions: managing data read (or load) and write (or store) operations.


## 3.3.1 Load Instructions

The read operation consists of the RISC-V core obtaining the value of a position using its memory address and placing it in an internal register. The RISC-V kernel, being a 32-bit architecture, works primarily with 4-byte words, where the addresses reference 4-byte words, as this is the size of the kernel's registers. The core, however, can access "chunks" of this word (of 1 or 2 bytes).

Listed below are the RISC-V loading instructions:

- lw: Reads a 4-byte word.

- lh: Reads a 2-byte word (with sign)

- lb: Reads a 1-byte word (with a sign).

- lhu: Reads a 2-byte word (unsigned).

- lbu: Reads a 1-byte word (unsigned).

Instructions that access less than 4 bytes need to choose how they will populate the rest of the register. The lh and lb instructions fill the rest of the register bits with the signal bit (MSB) value of the read value (signal extension). In this way, when reading a value of negative 1 byte (with bit 7 equal to 1) the other 3 bytes of the register will be filled with value 1, keeping the negative value.

The lhu and lbu instructions fill the rest of the register's bits with zero (extension of zeros). Thus, when reading a value of 1 byte that has no signal (bit 7 should not represent a signal) the other 3 bytes of the register will be filled with a value of 0, keeping the full value.

## 3.3.2 Store Instructions

The write operation consists of the RISC-V core writing the value of an internal register to a position using its memory address. As with loading, the kernel can write only "parts" of the word from memory.

Listed below are the RISC-V store instructions:

- sw: Write a 4-byte word.

- sh: Write a 2-byte word.

- sb: Write a 1-byte word.

These instructions then provide RISC-V with the ability to write an entire word into memory (with sw) or smaller parts (with sh and sb). Unlike load instructions , there is no need to extend the value, since, as much as the memory is divided into 4-byte words, each byte of this word is addressable.

Therefore, LSU must control the store operation, establishing which part of the memory word should be modified. LSU then emits a signal called a 4-bit byte write, where each one defines which of the four bytes of the word will be written. In addition, you must position the dice to be written in the desired position of the word. It is worth remembering that sw is aligned at 4 bytes, sh at 2 bytes, and sb at 1 byte.

For example, to write the 0x12 data in the 0x10010002 address (in Table 12) the LSU must inform that the third byte of the word in the 0x0000 position will be written (with a write byte equal to 01002), positioning the data correctly (becoming 0x00120000). Thus, the DMEM will write only the third byte!

## 4.2 Instruction Memory (IMEM)

This memory contains the program (or firmware) to be read and executed by the RISC-V core.

The IMEM has a simple implementation, being only a ROM containing the instructions to be executed. Upon receiving the memory address to be accessed and a read signal ( output enable), the 32-bit instruction that was in that position is received by the kernel to be executed.

In addition to holding instructions, the IMEM can maintain constant values that can be read by the CPU while running a program. For example, the

0x004000A0 : 0x00032283 : LW T0, 0(T1)

is located at IMEM, at the address 0x004000A0. Therefore, when the CPU sends this address in the seek cycle, it will receive the value 0x00032283 (hexadecimal equivalent to the instruction stored in memory), which corresponds to the load instruction. When executing, it will use t1 as a memory pointer, and assuming that t1 has a value 0x00400100 the IMEM will be accessed again, but not to read an instruction, but rather a constant value, which according to Table 14 is the value 10.

The IMEM also contains addresses aligned in 4 bytes, that is, with the bottom two bits always zero (for example 0x00400000, 0x00400004, 0x00400008, etc.).

## 4.3 Data Memory (DMEM)

This memory contains the data used during the execution of the program by the RISC-V core, the variables. It is in the DMEM memory that the variables are kept:

- Global: In a part of memory called .data.

- Uninitialized: In a portion of memory called .bss.

- Local (or temporary): In a part of memory called the stack.

- Dynamics: In a part of memory called the heap.

DMEM is implemented using SRAM memory cells with synchronous read and write. Thus, when performing a write (via sw, sh and sb instructions) or a read (via lw, lh, lb, lhu and lbu instructions) the operation will only be completed after a clock cycle.

DMEM, internally, addresses 4-byte words instead of 1-byte, that is, it contains addresses aligned in 32 bits, ignoring the bottom two bits of the address (e.g., 0x10010000, 0x10010004, 0x10010008, etc.). Even so, the memory must allow the independent writing of each byte of these 4-byte words (via sh and sb statements), as required by section 3.3. LSU (Load/Store Unit) of the RISC-V specification [1].

To make this possible, the memory maintains n 4-byte words, where n is the total size of the memory in bytes divided by 4. Thus, a 256-byte memory contains 64 words of 4 bytes, for example. The kernel then executes sh (store half, writes 2 bytes) or sb (store byte, writes 1 byte) requests (via LSU bw_o ) that parts of a word can be written. Memory must then use this signal to select which bytes of the word memory to write.

## 4.4 Address Decoder


This component acts as an intermediary between the RISC-V core and the memory devices, all accessed through memory addresses (a strategy known as MMIO) and load and store instructions, isolating the address space of multiple devices.

Its operation is based on receiving a memory address from the RISC-V core and verifying which device is mapped to that address, selecting it for the load or store operation, routing the necessary signals according to the device (described below).

Figure 3 contains the block diagram of the address decoder, showing its main internal components and their interconnections:

*Figure 3.*

*Address Decoder Block Diagram*

The core emits four different control signals (in addition to the data input and output buses), which must be routed to the devices by the decoder:

- It sends the address signal (coming from the address_o port of the core) to all devices, ignoring the bottom two bits (alignment at 4 bytes).

- Emits the write signal (Write Enable, coming from the we_o port of the core) to all devices, EXCEPT IMEM memory, which cannot be written.
