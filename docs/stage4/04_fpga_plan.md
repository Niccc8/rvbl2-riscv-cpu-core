# Stage 4 FPGA plan: `riscv.sv` for the organisers' `top.sv` (for GATE 2)

**Status:** plan only, nothing built. Ground truth: `01_aws_reference.md` (re-checked 2026-10-10:
organisers' Stage 4 repo still `b748304`, `top.sv` sha256 `0fd73910…`; `emu.c` `31e4ca7c…`).
**Goal:** one AWS synthesis (~45 min of VM time), right the first time.

## 1. The decision in one paragraph

We paste **two files**: the organisers' `top.sv` **byte-for-byte unchanged**, and one
`riscv.sv`, **generated by a script from `rtl/`** (never hand-edited). Inside `riscv.sv`, a thin
FPGA-only shell module `RISCV` divides the 250 MHz `clk_main_a0` down to **31.25 MHz** with an
**MMCM**, synchronises reset and pins, and runs our **unchanged, verified core** as instance
`e_PROCESSOR`. The firmware (LaneX protocol v4) is a literal ROM inside the file, equal to
`firmware.hex` bit for bit. The `RISCV` shell also provides the `Transmitter`/`Receiver` that
`top.sv` instantiates.

## 2. Why not run the core at 250 MHz

`top.sv` feeds `RISCV` with `clk_main_a0` = 250 MHz (4 ns). Our core is a multicycle design that
was signed off at 33 ns (Sky130). Its longest path in one cycle is register-file read →
32×32 multiply (DSP cascade) → write-back mux → register write; the combinational IMEM case-ROM
read feeds the instruction register in one cycle too. Estimated 80–140 MHz on the VU47P (old
Yosys estimate, `01` R9). Pipelining the core to 250 MHz would rewrite verified RTL four days
before the event: **rejected**. Dividing the clock **inside our own module** keeps `top.sv`
untouched and the core exactly as verified.

**Why 31.25 MHz (÷8):** it is the ASIC's own operating point (30.3 MHz), so every firmware
timing budget validated so far still holds (byte-time 2,713 cycles vs 2,630; receive wait
≤ 199 cycles; hold-off; ROM measurement), and an 8× slack over the estimated core speed makes
timing a non-issue. The UART divider becomes `round(31.25 MHz / 115,200) = 271` (115,314 bps,
+0.09 %; `top.sv`'s side: 2,170 at 250 MHz = 115,207 bps; mismatch 0.09 %, limit ~2 %).

> The organisers' README *describes* the processor as using `clk_main_a0` directly, and says
> the `riscv_clk` connection on the right must be preserved. It does not forbid dividing the
> clock inside our module. **Conflict to flag (Q1):** if the organisers require the core itself
> to run at 250 MHz, this plan changes. Cheap to ask them before the build.

## 3. `riscv.sv` architecture

```text
RISCV                      ports exactly as top.sv expects: i_Rx_Serial, i_Clk, i_nRst,
│                          o_Tx_Serial, io_Pins[7:0]  (so top.sv needs ZERO edits)
├─ u_mmcm   MMCME4_BASE    CLKIN 250 MHz (4.0 ns), VCO = 250 × 4 = 1000 MHz (legal 800–1600),
│                          CLKOUT0 ÷32 = 31.25 MHz → BUFG → clk_core; RST tied 0; LOCKED used
├─ reset    rst_core = !LOCKED | !i_nRst, 2-FF synchronised into clk_core (async assert,
│                          sync release); the core keeps its own synchronous active-high reset
├─ e_PROCESSOR : rvbl2_top our chip (rtl/top.v, renamed), UART_CLK_FREQ_HZ = 31_250_000
│   ├─ wire [31:0] w_PC_Output   ← the core's PC, so top.sv's `riscvtop.e_PROCESSOR.w_PC_Output`
│   │                              resolves exactly as in the organisers' reference build
│   ├─ pins: assign pins_io[n] = gpio_oe[n] ? gpio_o[n] : 1'bz   (unchanged rtl pattern,
│   │        the same tri-state idiom top.sv uses; Vivado converts both to logic)
│   ├─ pin inputs: 2-FF synchroniser in clk_core (FPGA variant only; see §5)
│   ├─ rvbl2_imem: literal `case` ROM, 2,799 words = firmware.hex (no $readmemh)
│   └─ rvbl2_dmem: 2,048 × 32 synchronous RAM, byte enables → 2 × RAMB36 (no `(* keep *)`)
├─ Transmitter #(p_CLKS_PER_BIT)  i_Clk,i_Rst,i_Tx_Transmit,i_Tx_Byte,o_Tx_Serial,o_Tx_Done
│     idle-high (also in reset); one byte per 1-cycle i_Tx_Transmit; o_Tx_Done = sticky LEVEL
│     (1 from reset and after each byte, 0 while sending) — emu polls it 50 ms later
└─ Receiver    #(p_CLKS_PER_BIT)  i_Clk,i_Rst,i_Rx_Serial,o_Rx_Done,o_Rx_Byte
      2-FF synchroniser on i_Rx_Serial (it comes from our 31.25 MHz domain); o_Rx_Done = ONE
      cycle per byte (top.sv advances its FIFO walker every cycle it is high)
```

### 3.1 The exact diff against the organisers' `top.sv`

**None.** Line by line, the only lines the README lets us change, and why each stays:

| `top.sv` line | Allowed change | Ours | Why no edit is needed |
|---|---|---|---|
| `RISCV riscvtop (` | module name | `RISCV` | We name our shell module `RISCV` |
| `.i_Rx_Serial (w_Rx),` | left name | same | Our shell's port is named `i_Rx_Serial` |
| `.i_Clk (riscv_clk),` | left name | same | `i_Clk` |
| `.i_nRst (riscv_nreset),` | left name | same | `i_nRst`, active low as given |
| `.o_Tx_Serial (w_Tx),` | left name | same | `o_Tx_Serial` |
| `.io_Pins (io_Pins)` | left name | same | `io_Pins` |
| `3'b111: … riscvtop.e_PROCESSOR.w_PC_Output;` | path or `32'b0` | same | Our instance is `e_PROCESSOR` and holds a wire `w_PC_Output` |

The pre-flight gate checks `sha256(top.sv) == 0fd73910…` so a stray edit cannot slip in.
**Fallback, one line:** if Vivado rejects the hierarchical reference, replace that line with
`32'b0` (the README allows it); PC readback is then lost, the demo is not.

### 3.2 Generator rules (`scripts/stage4/gen_riscv_sv.py`, one source of truth)

1. Read `rtl/*.v` (not copies). Prefix **every** module with `rvbl2_` (`top` → `rvbl2_top`):
   no clash with `top`, `tick_gen`, `Transmitter`, `Receiver` or HDK names (R3).
2. FPGA-only transforms, each applied by exact text match and **asserted to match once**:
   `riscv_core` gains `output [31:0] pc_o` (= the existing `pc` wire); `rvbl2_top` gains
   `wire [31:0] w_PC_Output = pc_o` and the pin synchroniser; `dmem` loses `(* keep *)`;
   `imem` becomes the case ROM. `rtl/` itself is not modified: the ASIC sign-off stays valid.
3. No `` `timescale ``, `` `default_nettype `` or `` `define `` in the file (they would leak into
   `top.sv`, which is compiled in the same session), no `initial` blocks, no file I/O, no
   simulation-only constructs; no module named like a Xilinx primitive.
4. Parameters: `--clk-hz 31250000` (AWS) or `30303030` (ChipInventor). The divider follows.
5. Header records the source commit, `firmware.hex` sha256 and the ROM CRC the `I` record must
   report, so the hardware answer can be compared with the file.

## 4. Firmware strategy: one bitstream, everything in it

- **Image:** LaneX protocol v4 (`application/firmware/out/lane/firmware.hex`, 2,799 words), the
  firmware every regression runs. Nothing FPGA-specific in C: the clock only changes the UART
  divider, which lives in the RTL.
- **Why no FPGA-only firmware:** a firmware change is a new 45-min synthesis (`01` §1). The
  current image already answers every demo line (12 `./emu` lines incl. authentication and
  identify).
- **The organisers' own test line** (`./emu -d 0xF0 -i 0x02 -t1 0x30 -r1 0x30 -o 0x20`) is for
  **their** echo firmware; on ours it fails by design (we answer frames, not echoes). The runbook
  says so; if judges insist on it, see §8 option B.

### 4.1 Bring-up ladder (on the F2, each step needs the previous one)

| Step | Command | Proves |
|---|---|---|
| 0 | `./axil_rw read 0 0x1C` twice, 1 s apart | Image loaded, MMCM locked, core running: PC changes, inside `0x0040_0000–0x0040_2BBC` |
| 1 | manual reset (`axil_rw write 0 0x00 0/1`), then `./emu -d 0xF0 -o 0x00` | Pins and `OUT` path; lane open, no lamps |
| 2 | `./emu` **identify** line | UART both ways at 115,200; the ROM CRC equals this build's |
| 3 | `./emu` **charged** line | GPIO in/out, tag CRC, decision, record |
| 4 | the remaining 10 lines | Every outcome, authentication |

## 5. Clock-domain crossings (all paths between related clocks; Vivado times them)

| Crossing | From → to | Handling |
|---|---|---|
| `i_Rx_Serial` | `top.sv` Transmitter FF (250) → our UART | `uart.v` already has a 2-FF synchroniser |
| `o_Tx_Serial` | our UART FF (31.25) → `Receiver` | 2-FF synchroniser inside our `Receiver` |
| `io_Pins` in | `input_pins` reg (250) → our GPIO | **new** 2-FF synchroniser in `rvbl2_top` (FPGA variant): keeps the path short instead of running through the whole read-data mux under a 4 ns budget |
| `io_Pins` out | our GPIO FF (31.25) → `cl_ocl_rdata` (250) | short path; read 50 ms after the change by emu |
| `i_nRst` | `riscv_nreset` (250) → reset sync | 2-FF synchroniser |
| `w_PC_Output` | PC (31.25) → `cl_ocl_rdata` (250) | multi-bit; a read can catch a PC mid-update only as a value that is still a valid recent PC; bring-up only |

| # | Check | Tool | Pass criterion |
|---|---|---|---|

| G5 | Synthesizability | Yosys 0.33 `synth_xilinx -family xcup` | no latches, no multi-driven nets, no file dependencies; DMEM → RAMB36, multiplier → DSP48E2; LUT/FF/BRAM/DSP counts |

| G7 | Mutations the sim must catch | G3 | divider for 250 MHz (2,170) in our UART; reset polarity inverted; firmware `DATADIR` ≠ `0xF0`; `o_Tx_Done` as a pulse (emu hangs → timeout); `o_Rx_Done` held 2 cycles (FIFO skips) |

## 7. Risk register

| # | Risk | L | I | Mitigation |
|---|---|---|---|---|
| R1 | Organisers require the core at 250 MHz (no internal divider) | L | H | Ask before building (Q1). Fallback: BUFGCE_DIV is also a divider; a real fallback is a CE-gated core (§8 C) |
| R2 | MMCM driven by `clk_main_a0` rejected by a DRC / fails to lock in the partial-reconfiguration region | L | H | AWS's own AWS_CLK_GEN puts MMCMs in the CL fed by a shell clock (F2 docs, accessed 2026-10-10); LOCKED gates our reset; step 0 of the ladder detects "no lock" (PC frozen). Alternative primitive: BUFGCE_DIV ÷8 (generator switch) |
| R3 | Hierarchical PC reference not resolved | L | H (build fails) | Exact depth of the organisers' working build; fallback `32'b0` |
| R4 | Phantom vehicle in emu's start-up window | M | M | G4; the PDF's hardware result says a disabled driver reads 0 |
| R5 | Web editor chokes on a large file (case ROM ≈ 2,800 lines) | L | M | Size measured in G1; split into two `.sv` files if > a few hundred kB |
| R6 | Timing failure on the 4 ns cross-domain paths | L | L | Synchronisers keep them to 1–2 LUTs; the organisers' own 250 MHz build produced a working AFI |
| R7 | Paste error (missing line, wrong file) | M | H | Runbook: compare line count and the header's sha256 in the editor before Save |
| R8 | Judges run the organisers' echo test line | M | L | Explain; §8 B if required |

## 8. Options considered and not recommended

| Option | Verdict |
|---|---|
| **A. UART-loadable IMEM** (a bootloader in ROM loads firmware into a RAM IMEM over `0x0C`) | **Not now.** Makes firmware changeable without synthesis, but: emu sends ~10 bytes/s (an 11 kB image = ~19 min per load, lost at every emu reset); a fast loader needs our own host tool and `axil_rw` loops; it changes the verified IMEM and boot path. Our image is feature-complete. Roadmap (P2), and a good pitch line ("field-updatable" is a production feature) |
| B. Two images in one ROM (ours + an echo mode for the organisers' test line), selected at boot by a pin | Possible (~200 words of ROM), but emu's start-up window makes boot-time pin selection unreliable. Only if the organisers say their test line is mandatory |
| C. Core at 250 MHz with a clock enable (every register gated, no new clock) | No primitive risk, but every always block of verified RTL changes and Vivado reports thousands of setup "violations" without multicycle constraints (we can supply no XDC). Fallback only if R1 bites |
| D. Pipeline the core to 250 MHz | Rewrites verified RTL; days of work; rejected |
