# SRAM Macro (optional DMEM realization)

## What is here

| File | Purpose |
|---|---|
| `sky130_sram_2kbyte_1rw1r_32x512_8.v` | Behavioral model, for simulation |
| `sky130_sram_2kbyte_1rw1r_32x512_8_sim.v` | Thin local wrapper adding a `timescale` — compile this one |
| `sky130_sram_2kbyte_1rw1r_32x512_8.lef` | Abstract view, for placement and routing |
| `sky130_sram_2kbyte_1rw1r_32x512_8_TT_1p8V_25C.lib` | Timing/area, for synthesis and STA |

**Not included:** the `.gds` (14 MB) and the `.sp`/`.lvs.sp` SPICE views. A physical
flow needs the GDS for the final stream-out and the SPICE for LVS; fetch them from
the upstream repository alongside these files when running one.

## Provenance

Generated by [OpenRAM](https://github.com/VLSIDA/OpenRAM) and distributed by
Efabless as [`efabless/sky130_sram_macros`](https://github.com/efabless/sky130_sram_macros)
under the Apache License 2.0. These files are **third-party IP, unmodified** — the
wrapper `_sim.v` is ours, and it only adds a `timescale` around an `include` of the
vendor file, leaving the vendor source byte-identical to upstream.

This matters for Submission Guide Note 1: the RTL and testbenches in this repository
are the team's own work; this directory is a clearly-labelled, permissively-licensed
third-party memory compiler output, used the way any SRAM macro is used.

## Why this macro

`dmem` needs 2048 × 32 bits (8 kB, Block Guide Table 6/13) with **independent
per-byte writes** — `SB` and `SH` cannot be implemented without a write mask. This
macro is 512 × 32 with `wmask0[3:0]` at 8-bit granularity, so four of them banked on
`address[12:11]` give exactly the required window.

Of the macros upstream ships, only two are usable here:

| Macro | Organisation | Footprint | Area | Verdict |
|---|---|---|---:|---|
| `sky130_sram_2kbyte_1rw1r_32x512_8` | 512 × 32 | 683.10 × 416.54 µm | 284,538 µm² | **Used** — 4× gives 8 kB |
| `sky130_sram_1kbyte_1rw1r_32x256_8` | 256 × 32 | 479.78 × 397.50 µm | 190,712 µm² | Works, but 8× is 34% larger |
| `sky130_sram_16kbyte_1rw1r_32x4096_8` | 4096 × 32 | — | — | **Unusable** — upstream ships only a `.log`, no GDS/LEF/LIB/model |
| `sky130_sram_1kbyte_1rw1r_8x1024_8` | 1024 × 8 | — | — | Wrong width |
| `sky130_sram_4kbyte_1rw1r_128x256_128` | 256 × 128 | — | — | Wrong width |

Port 1 (the read-only port) is unused — the core has a single memory interface — so
it is tied off (`csb1` high).

## Enabling it

The macro is **opt-in**. Without the define, `rtl/dmem.v` compiles to a plain
behavioral register array and does not reference the macro at all, so the design has
no dependency on any of these files. That is the default deliberately: a platform
that does not expose a macro library still builds the design unchanged.

```bash
# Simulation - the whole suite, against the macros
DMEM_MACRO=1 bash scripts/run_all.sh

# Synthesis - blackbox the macro via its .lib
yosys -p "read_liberty -lib macros/sky130_sram_2kbyte_1rw1r_32x512_8_TT_1p8V_25C.lib; \
          read_verilog -DSYNTHESIS -DDMEM_USE_SRAM_MACRO -sv rtl/*.v; ..."
```

For a place-and-route flow, add `EXTRA_LEFS`, `EXTRA_LIBS`, `EXTRA_GDS_FILES` and a
`MACRO_PLACEMENT_CFG` entry for each of the four instances (`u_sram0`–`u_sram3`), and
keep the PDN off the macro footprints.

## Measured effect

Sky130-mapped, same configuration, same non-flattened synthesis both ways:

| | Behavioral array | 4 × SRAM macro | Change |
|---|---:|---:|---:|
| `dmem` | 2,433,350 µm² | 1,139,191 µm² | −53.2% |
| Rest of SoC | 123,986 µm² | 124,354 µm² | +0.3% |
| **Total** | **2,557,336 µm²** | **1,263,545 µm²** | **−50.6%** |
| Flip-flops | 66,560 | ~1,050 | −98% |

The flip-flop count is the number that matters most for place-and-route: 65,536 of
them existed only to store DMEM. Removing them is what turns this from a congested,
slow P&R run into a routine one. The die-area gain is also larger than the cell-area
gain suggests, because a macro is a hard footprint while standard cells are placed at
some utilisation — 2.43 mm² of cells at 35% utilisation needs roughly 6.9 mm² of core.

## Behavioural differences worth knowing

Both realizations are verified equivalent for every access this core generates — the
full testbench suite passes either way, and 20 randomized programs match an
independent instruction-set simulator in both modes. Two differences are real and
deliberate, though:

1. **Power-up contents.** The behavioral array zero-fills for simulation
   determinism; a real SRAM powers up **undefined**, and the macro model reflects
   that. Firmware that reads `.bss` before initialising it gets zeros in one and
   garbage in the other. Correct startup code always zeroes `.bss` first, but this is
   worth re-checking against the official validation firmware when it is released.
2. **Read-data arrival within the cycle.** The behavioral array presents read data at
   the capturing clock edge; the macro presents it part way through the following
   cycle (its model drives `dout` to `x` at the edge, then assigns the word after an
   internal negedge-plus-delay path). Both are valid well before the next edge, which
   is where the register file samples load data, so the core is unaffected — but a
   testbench that samples immediately after the edge will see `x` from the macro.
   `tb_dmem`'s `do_read` samples late for exactly this reason.
